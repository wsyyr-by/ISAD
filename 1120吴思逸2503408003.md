# 古籍文献数字化平台 —— 面向服务架构（SOA）系统设计作业

## 问题 1：面向服务设计

### 1. 服务边界划分与核心服务清单

划分原则：**按业务能力划分，而不是按数据库表或页面划分**；每个服务只负责一类内聚能力，服务内部数据私有，对外只暴露接口，避免两个服务同时拥有同一数据的写权限。

#### （1）基础能力服务（可复用、与具体古籍业务流程无关）

| 服务名称                      | 服务职责                                              | 不负责的边界                 |
| ------------------------- | ------------------------------------------------- | ---------------------- |
| 统一身份认证与权限服务（AuthService）  | 用户登录、令牌签发与校验、角色/权限判定、古籍访问控制策略（开放/校内访问/涉密管控）的统一执行  | 不保存古籍业务数据，不决定业务审核流程    |
| 对象存储与文件服务（FileService）    | 影像等大文件的上传、下载、分片、存储键生成、文件校验、访问URL签发、生命周期管理         | 不理解OCR和实体标注语义，不保存业务元数据 |
| OCR识别服务（OCRService）       | 接收影像存储键，调用可替换的OCR引擎，返回文本、版面区域及置信度；适配不同OCR引擎       | 不保存古籍业务主数据，不负责人工校对     |
| 实体标注服务（AnnotationService） | 对OCR文本做人名、地名等实体识别/候选标注，提供实体标注的通用能力，可被检索、专题汇编等服务复用 | 不负责古籍元数据管理与标注结果审核      |
| 消息事件服务（EventBus，基础设施）     | 可靠事件发布/订阅、失败重投与死信处理，作为服务异步协作的基础设施                 | 不处理具体业务逻辑              |
| 操作审计服务（AuditService）      | 统一记录“谁、何时、修改了哪条记录”、变更前后摘要、请求来源；提供只读审计查询           | 不参与业务状态流转，业务方只投递审计事件   |

#### （2）业务服务（拥有古籍业务数据与状态）

| 服务名称                         | 服务职责                                                 |
| ---------------------------- | ---------------------------------------------------- |
| 古籍元数据服务（CatalogService）      | 古籍书目/元数据著录、版本与分类管理、公开级别维护、影像与OCR关联关系维护；是古籍主数据的唯一所有者  |
| 影像资源服务（ImageResourceService） | 影像上传流程、图像预处理与切图、页码与图组管理、影像与古籍的绑定；内部调用FileService存取文件 |
| 文本校对服务（TextService）          | OCR文本的校对任务、版本管理、差异保存、定稿发布；内部调用OCRService获取识别结果       |
| 标注审核服务（ReviewService）        | 标注任务的分配、人工校核与审核、审核状态流转；审核通过后发布实体标注结果                 |
| 检索与目录浏览服务（SearchService）     | 按权限过滤后的书目检索、全文检索、人物/地名检索；读取OCR文本与标注结果，建立检索索引         |
| 专题汇编与导出服务（CollectionService） | 专题数据集的组稿、导出、共享链接管理；导出前统一做权限校验                        |
| 对外集成网关（IntegrationGateway）   | 面向图书馆门户、学术成果系统提供统一API、限流、协议适配与调用审计；不直接读写其他服务的数据库     |

#### （3）编排服务（只负责跨服务流程，不拥有业务数据）

| 服务名称                                | 编排的核心流程                                                       |
| ----------------------------------- | ------------------------------------------------------------- |
| 数字化处理编排服务（DigitizationOrchestrator） | 影像上传完成 → 生成缩略图 → OCR识别 → OCR文本入库 → 实体候选标注 → 通知审核；负责流程状态、补偿和重试 |
| 发布共享编排服务（PublishingOrchestrator）    | 元数据审核、文本定稿、标注审核均完成后，统一更新发布状态，触发检索索引刷新，并向外部系统发布变更事件            |

> 服务职责不重叠示例：OCRService只“识别”，TextService只“管理校对版本”，ReviewService只“审核”，DigitizationOrchestrator只“串流程”；任一服务都不能绕过CatalogService直接修改古籍主数据。

### 2. 任选两个服务的接口契约（JSON风格）

#### 服务一：OCR识别服务（基础能力服务）

- **服务名称**：OCRService
- **服务职责**：对指定影像执行文字识别，返回带版面位置和置信度的文本；支持切换OCR引擎，调用方不感知具体引擎实现。

**入参：**

```json
{
  "requestId": "REQ-20261120-0001",
  "imageRef": {
    "fileId": "IMG-10001",
    "storageKey": "ancient/10001/page-001.tif",
    "sha256": "9f86d081884c7d65..."
  },
  "options": {
    "engine": "engine-a",
    "language": "zh-Hans",
    "layoutAnalysis": true,
    "returnConfidence": true
  },
  "callback": {
    "type": "WEBHOOK",
    "url": "https://internal/ocr/callback",
    "topic": "ocr.completed"
  }
}
```

**出参（任务已受理，文本稍后异步返回；若采用同步识别则可直接返回下方 `result` 内容）：**

```json
{
  "code": 0,
  "message": "ACCEPTED",
  "data": {
    "taskId": "OCR-TASK-9001",
    "status": "QUEUED",
    "estimatedSeconds": 30
  }
}
```

```json
{
  "requestId": "REQ-20261120-0001",
  "taskId": "OCR-TASK-9001",
  "status": "SUCCEEDED",
  "engine": "engine-a",
  "result": {
    "fullText": "……OCR识别正文……",
    "averageConfidence": 0.93,
    "blocks": [
      {
        "blockId": "B1",
        "text": "……",
        "bbox": [120, 85, 960, 240],
        "confidence": 0.91
      }
    ]
  }
}
```

**异常返回：**

```json
{
  "code": "FILE_NOT_FOUND",
  "message": "storageKey对应的影像文件不存在",
  "data": { "storageKey": "ancient/10001/page-001.tif" },
  "retryable": false,
  "traceId": "TRACE-7b1e..."
}
```

其他约定异常：`INVALID_IMAGE_FORMAT`（不可重试）、`ENGINE_UNAVAILABLE`（可重试）、`ENGINE_TIMEOUT`（可重试）、`RATE_LIMIT_EXCEEDED`（可重试）、`INTERNAL_ERROR`（可重试，幂等键去重）。

> 幂等约定：`requestId` 为幂等键；同一请求重复提交不会生成两个OCR任务。引擎名称只是选项，业务逻辑不依赖某一家OCR厂商。

#### 服务二：目录检索服务（业务服务）

- **服务名称**：SearchService
- **服务职责**：在权限过滤后，对古籍书目、OCR全文和实体标注进行统一检索；只读取索引，不修改业务主数据。

**入参：**

```json
{
  "requestId": "REQ-20261120-0002",
  "caller": {
    "userId": "U-2001",
    "roles": ["RESEARCHER"],
    "campusIp": true
  },
  "query": {
    "keyword": "苏州府志",
    "scope": ["TITLE", "FULL_TEXT", "ENTITY"],
    "entityType": "PERSON",
    "filters": {
      "dynasty": "清",
      "category": "地方志"
    }
  },
  "pagination": { "page": 1, "pageSize": 20 }
}
```

**出参：**

```json
{
  "code": 0,
  "message": "OK",
  "data": {
    "total": 2,
    "page": 1,
    "pageSize": 20,
    "items": [
      {
        "bookId": "B-10001",
        "title": "苏州府志",
        "accessLevel": "OPEN",
        "dynasty": "清",
        "match": {
          "type": "ENTITY",
          "entityName": "某某",
          "highlight": "……<em>某某</em>……"
        },
        "canDownload": true
      }
    ]
  }
}
```

**异常返回：**

```json
{
  "code": "ACCESS_LEVEL_EXCEEDED",
  "message": "当前用户无权检索涉密管控文献",
  "data": { "requestedAccessLevel": "RESTRICTED" },
  "retryable": false,
  "traceId": "TRACE-2c4f..."
}
```

其他约定异常：`INVALID_PARAM`（关键词为空、分页参数非法）、`INDEX_UNAVAILABLE`（索引重建中，可重试）、`UPSTREAM_TIMEOUT`（可重试）。

> 权限约束：`caller` 中的身份由网关注入且不可信任客户端自填；检索前必须先按 `accessLevel` 过滤，校内访问类要求校园IP或校内角色，涉密管控类不进入普通检索结果。

### 3. 服务解耦方式与同步/异步调用场景选择

#### （1）解耦手段

1. **接口契约与版本化**：所有接口使用时序JSON风格契约、幂等键和明确错误码；接口路径带版本（如 `/v1/ocr/tasks`），提供方升级不破坏调用方。
2. **服务私有数据库**：每个服务独占自己的数据表，其他服务不能直连；CatalogService是古籍主数据唯一写入口，OCR服务通过 `bookId + pageId + fileId` 引用，而不复制书名、权限等业务字段。
3. **事件驱动**：文件上传完成、OCR完成、标注审核通过等状态变化以领域事件发布；`DigitizationOrchestrator` 编排流程，OCR、标注等服务之间不直接互相调用。
4. **适配器隔离外部依赖**：OCR引擎通过统一适配器替换；数据库通过 Repository 接口隔离；对象存储通过FileService隔离，更换引擎或数据库不影响业务服务。
5. **统一权限与审计**：权限策略集中在AuthService；AuditService通过订阅事件统一留痕，避免每个服务各写一套日志且遗漏“谁、何时、改了什么”。
6. **网关隔离上层系统**：图书馆门户和学术成果系统只对接IntegrationGateway，平台内部服务拓扑变化对外部透明。

#### （2）同步调用场景

- 需要**立即拿到结果才能继续**的操作：登录鉴权、权限判定、书目详情、目录浏览、简单检索、公开影像缩略图URL获取。
- 操作本身**耗时短、结果确定**：元数据保存、审核状态提交、导出任务创建等。
- 采用超时、重试（仅幂等操作）、熔断和降级；外部门户查询以同步REST/gRPC为主。

#### （3）消息队列异步调用场景

- **耗时且无需用户等待**的处理：OCR识别、缩略图/切图生成、实体候选标注、全文索引重建、专题数据导出。用户提交后得到 `taskId`，完成后通过回调或消息通知。
- **跨服务状态传播**：`ImageUploaded → OCRRequested → OCRCompleted → AnnotationRequested → AnnotationCompleted → ReviewRequested → Published` 这类流程通过消息队列串联，任一环节失败可重试而不丢失事件。
- **需要削峰与最终一致性**：批量上传古籍影像时，消息进入队列后由OCR服务按能力消费，避免瞬时并发压垮OCR引擎。
- **审计留痕**：业务事件投递到AuditService，审计写入不阻塞主业务；审计失败进入死信队列并告警补录。

**判断原则**：用户正在等待且要求结果强一致 → 同步；可后台处理、允许秒级到分钟级延迟、需要削峰或跨服务状态传播 → 消息队列异步。异步场景通过幂等键、事务消息/Outbox、死信队列和补偿任务保证最终一致，不追求跨服务分布式事务。

### 2. 核心数据表设计

> 约定：`BIGINT` 主键采用雪花ID或数据库序列；`created_at`/`updated_at` 为 `DATETIME(3)`；`is_deleted` 为软删除标记；MySQL 8.0 / InnoDB 语法示例。唯一约束用 `UQ_`，普通索引用 `IDX_`。

#### （1）古籍主表 `book`

| 字段                          | 类型                                            | 约束                               | 说明           |
| --------------------------- | --------------------------------------------- | -------------------------------- | ------------ |
| `book_id`                   | BIGINT                                        | **PK**, NOT NULL                 | 古籍唯一标识       |
| `title`                     | VARCHAR(255)                                  | NOT NULL                         | 书名           |
| `creator`                   | VARCHAR(255)                                  | NULL                             | 责任者          |
| `edition`                   | VARCHAR(255)                                  | NULL                             | 版本           |
| `dynasty`                   | VARCHAR(32)                                   | NULL                             | 朝代           |
| `category_id`               | BIGINT                                        | NULL, FK→`category(category_id)` | 分类           |
| `call_number`               | VARCHAR(64)                                   | NULL, **UQ**                     | 馆藏号          |
| `access_level`              | ENUM('OPEN','CAMPUS','RESTRICTED')            | NOT NULL, DEFAULT 'RESTRICTED'   | 开放/校内访问/涉密管控 |
| `metadata_status`           | ENUM('DRAFT','PENDING','APPROVED','REJECTED') | NOT NULL                         | 元数据审核状态      |
| `publish_status`            | ENUM('DRAFT','PUBLISHED','OFFLINE')           | NOT NULL                         | 发布状态         |
| `created_by`                | BIGINT                                        | NOT NULL, FK→`user(user_id)`     | 创建人          |
| `created_at` / `updated_at` | DATETIME(3)                                   | NOT NULL                         | 创建/更新时间      |
| `version`                   | INT                                           | NOT NULL, DEFAULT 0              | 乐观锁版本号       |
| `is_deleted`                | TINYINT                                       | NOT NULL, DEFAULT 0              | 软删除          |

**索引**：`PRIMARY KEY(book_id)`；`UQ_book_call_number(call_number)`；`IDX_book_title(title)`；`IDX_book_creator(creator)`；`IDX_book_category_status(category_id, metadata_status)`；`IDX_book_access_publish(access_level, publish_status)`；全文检索交给SearchService的搜索引擎，不在业务库做 `LIKE '%...%'`。

#### （2）影像文件表 `image_file`

| 字段                          | 类型                                             | 约束                           | 说明                          |
| --------------------------- | ---------------------------------------------- | ---------------------------- | --------------------------- |
| `image_id`                  | BIGINT                                         | **PK**, NOT NULL             | 影像ID                        |
| `book_id`                   | BIGINT                                         | NOT NULL, FK→`book(book_id)` | 所属古籍                        |
| `file_name`                 | VARCHAR(255)                                   | NOT NULL                     | 原始文件名                       |
| `storage_key`               | VARCHAR(512)                                   | NOT NULL, **UQ**             | 对象存储键，非数据库内二进制              |
| `file_size`                 | BIGINT                                         | NOT NULL                     | 字节数，CHECK (`file_size` > 0) |

#### （7）辅助表（支撑范式与扩展）

- `category(category_id PK, category_name, parent_id FK)`：古籍分类。
- `ocr_task(task_id PK, image_id FK, engine_code, status, retry_count, error_message, created_at)`：OCR任务与重跑记录。
- `entity(entity_id PK, canonical_name, entity_type, alias_json)`：规范人物/地名实体。
- `review_record(review_id PK, target_type, target_id, reviewer_id FK, result, comment, reviewed_at)`：审核历史。

**范式检查**：实体属性只依赖各自主键，满足3NF；`book` 只保存元数据、不保存影像和OCR内容；重复出现的分类、实体、角色分别独立成表；`collection_book` 消除多对多冗余；OCR多版本通过 `version/is_final` 管理而非覆盖历史。对检索、展示等高频场景允许在SearchService的索引中做**受控冗余**（冗余书名与权限级别），但写回仍以主表为准，通过事件保证一致。

### 3. 为什么古籍影像文件不直接存入数据库表中

1. **体积与性能**：一张古籍大图常有几十MB甚至上百MB，直接作为BLOB存库会急剧放大数据库和数据文件，普通业务查询、备份、主从同步都要搬运这些二进制数据，导致I/O和缓存命中率恶化；文本、元数据查询也会被拖慢。
2. **数据库定位**：关系型数据库擅长事务、结构化查询和约束，不擅长海量大对象存取。影像应放在对象存储/分布式文件系统中，数据库只在 `image_file` 表保存 `storage_key`、大小、格式、SHA-256等元数据和关联关系（该表即“影像文件表”，存的是文件描述信息，不是文件二进制本身）。
3. **扩展与成本**：对象存储易水平扩容，成本低，并支持生命周期策略（热/冷存储）、CDN加速、断点续传和分片上传；数据库扩容昂贵且大对象会拉长恢复时间。
4. **访问与并发**：影像下载、缩略图请求是高并发流式读取，应由对象存储/CDN承担；数据库只处理短小事务，避免大量长连接被大文件传输占用。
5. **替换与解耦**：题目要求影像、OCR文本、元数据分开存储且未来可更换数据库或存储。数据库只存引用，更换对象存储或数据库时只需迁移元数据或调整FileService适配器，不需要搬迁整库二进制大对象。
6. **安全与审计**：对象存储可通过临时签名URL、私有Bucket和访问策略控制涉密影像；数据库保存权限级别、文件引用和操作日志，实现权限隔离与留痕，两者职责清晰。

> 一致性保障：先上传文件到对象存储并校验SHA-256，再在数据库写入记录；删除采用“先标记删除、后异步清理对象”的两阶段方式，避免库中有记录但对象已丢失或对象残留。
